# 1 理论篇


## 1.1 什么是Harness Engineering


Harness 这个词本意是"马具、挽具”，这个词的概念来自于OpenAI 工程师Ryan Lopopolo 在2026 年 2 月发的一篇文章——[_Harness engineering: leveraging Codex in an agent-first world_](https://openai.com/zh-Hans-CN/index/harness-engineering/)，原文中说了一段话：**Agent 搞砸的时候，解决办法不是"再跑一次试试"，而是退一步去想"缺了什么护栏？怎么让 Agent 看得懂、绕不过？"**


这句话说出了Harness Engineering核心要解决的问题：**以前是"告诉 AI 做什么"，现在是"建一个 AI 能自己转起来的环境"。怎么把 AI 从一个会临场发挥的模型，变成一个在工程里可约束、可协作、可校验、可持续维护的执行系统。**


所以可以用一句话解释Harness Engineering：**一套让 AI 在工程里稳定产出正确结果的工程系统。**


## 1.2 从Prompt时代到Harness时代


以开发一个代码学习网站为例，在prompt时代我们的方法是给AI发一句话“帮我写一个代码学习网站，需要用来……“，每次对话都是从零开始，一旦达到模型的上下文上限，我们就得新开一个窗口把项目背景再重新交代一遍。


因此我们想到一个办法：用说明文档来存放项目背景引导AI，我们可以把所有希望AI知道的东西写成markdown文档，它每次工作的时候就会去阅读，从而减少返工次数。但问题依旧存在：文档只能管“做什么”，管不了“怎么做”，文档会过时，而且知识点散落各处。


因此更好的解决方案是系统化，具体来说就是把不同用途的文档放到不同的文件夹里，比如：

1. **声明式规则**（`.cursor/rules/`）：把编码约束固化成规则文件，AI 每次启动都会加载
2. **技能封装**（`.cursor/skills/`）：把编译、测试之类的重复操作包装成一键可调的"技能"
3. **自动化验证**（`verify_all.ps1`）：改完代码后跑一遍自动检查，看有没有违规
4. **多 Agent 协作**（`.cursor/agents/`）：7 个角色各管各的，流水线作业
5. **基线管理**（`verification_baseline.json`）：量化指标只升不降，测试数量少了立刻报警

## 1.3 Harness包括什么


首先理解几个在Harness Engineering里关键的概念：


| **概念**    | **它主要回答什么问题**   | **在我们工程里的角色**         | 举例                                                   |
| --------- | --------------- | --------------------- | ---------------------------------------------------- |
| Rule      | 什么事绝对不能乱来       | 基础规矩、红线、底线            | 每次改完代码后都必须验证                                         |
| MCP       | AI 怎么安全接上外部工程系统 | 外接能力与工具链（含 Unity 等宿主） | 把外部系统以 Tool 的形式暴露给 AI，便于被 Rule、Workflow、Scripts 一起约束 |
| Skill     | 这件事具体应该怎么做      | 固定动作的标准操作手册           | 完成网址部署和云端服务器注册的说明书                                   |
| Sub Agent | 复杂任务由谁分工处理      | 不同阶段的专业角色             | 技术方案设计师、开发工程师、测试员、PM协同                               |
| Workflow  | 这些角色按什么顺序接力     | 前进、暂停、打回、重跑规则         | 上面这几个人按照什么顺序工作（设计师先提方案，工程师完成开发，测试员实现测试，PM推动全流程）      |
| Scripts   | 最后谁来判断到底做没做好    | 统一门禁和事后验证             | 具体的python脚本，比如看英文文档里有没有夹杂中文                          |


# 2 实践篇


了解Harness Engineering的概念之后，我们具体如何在工程中实现套马鞍？接下来就从零开始详细介绍一下实现流程。需要注意的一个前提是人和AI的分工：人搭Harness，AI写代码。


## 2.1 写设计规格文档（SPEC.md）


这个文档写这些内容：你想要开发一个什么工程，最终想交付什么样的东西，可以参考这个模版：

- 这个版本要解决什么问题
- 哪些问题是核心目标，哪些只是顺手优化
- 改动会影响哪些模块
- 哪些行为必须保持兼容
- 最终什么样才算做完

这个文档是在和AI的交流中迭代完成的，本身也是在加深我们对需求本身的理解，最终的SPEC必须写明你的**所有**需求，指明**必要**的边界条件（后面的需求分析agent会帮你补充 剩下的边界条件），必须**没有**任何不确定的词语，例如：建议，可以，推荐，可选等字样。


## 2.2 写规则文档（Rule.md）


这个文档解决的问题是**原则约束**，类似于系统提示词，告诉Agent你必须遵守的规则是什么，比如每次改完代码必须编译、测试和验证


## 2.3 写/找Skills


我们解决问题的时候，除了要让AI知道不能做什么（Rule.md），更关键的是让AI知道应该怎么做，好比给马安上马鞍的目的是让马跑起来，这个时候Skills的作用就体现了出来。比如前面我们在Rule.md里写”修改完代码后必须做编译测试“，那我就可以写一个Skil告诉Agent完整的测试流程是什么，需要从哪几个方面进行测试等等


## 2.4 拆分Sub Agent


一句话总结我们创建Sub Agent的方案：结构化调度，固定每个子Agent的角色和流程。


怎么拆这几个Agent呢？其实是在不停遇到问题的过程中逐渐出生的，还是拿网站开发举例：

1. 第一步，先拆需求分析、方案设计、开发实现

    模糊需求直接流进代码，但往往会有三个问题：需求边界不清晰，技术方案边做边想，做完之后也不知道思路。因此三个基础角色诞生了：

    - **需求分析** 负责把模糊想法变成结构化需求。
    - **方案设计** 负责把需求翻译成真正能落地的技术方案。
    - **开发实现** 负责按照前面的约束去写代码，而不是边写边定义需求。
2. 第二步，补上闸门总控

    只拆这三层，很快又不够用了。原因是： 需求写出来了，方案也写出来了，并不代表它真的已经具备进入网站开发的条件。我们在实际跑的时候，很快就遇到很多这种情况：开发真开工以后，才发现前面很多问题没人提前拦住。


    因此一个总控角色必须守在最后一道门上，专门用来判断这份需求是否清晰、方案是否全面、开发是否会有风险。


需要注意的是，不是所有agent都需要有一样智慧的大脑，比如推动流程的Agent，只需要一个相对普通的模型，而那些产生关键决策的Agent，需要有更为智慧的大脑支撑它提出创造性的方案。
